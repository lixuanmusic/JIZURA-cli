# JIZURA 批量生成 CLI — 设计文档

日期：2026-10-21
状态：待用户确认

## 意图与背景

用户手头有一批歌（音频 + 带逐行时间戳的 .lrc 歌词），希望每首歌各生成多个**指定主题**的视频版本（文字PV / 动态文字 / 和风 / 恐怖 / 流行 / 抒情），而不是在浏览器里一首首点。JIZURA 的生成引擎是纯浏览器端的（src/ 打包为单文件 index.html，`J.*` 全局暴露），没有服务器端入口。本工具用一个终端向导 + 无头 Chrome 复用现有引擎，**不改动引擎本身**。

## 目标

- 终端交互式向导：输入文件/文件夹路径 → 识别配对 → 多选主题 → 选画面比例、分辨率、FPS → 确认摘要 → 批量生成。
- 每首歌 × 每个选中主题各导出一个 MP4（音乐嵌入，节拍自动检测）。
- 进度可见：每个任务一条进度条（当前帧/总帧），并有整体序号（如 3/12）。
- 生成参数可追溯：种子与全部参数写入日志，失败不中断整批，最后汇总。

## 非目标（v1 不做）

- .trcx 逐字时间戳（用户明确推迟；引擎本身也只认行级时间戳）。
- 并行生成（视频编码吃满硬件，串行更稳）。
- 生成前预览/挑选；生成为静默批量出文件。
- 修改 src/ 引擎或 app 的任何行为。
- 服务器化、远程调用。

## 反目标（做了就算失败）

- 需要用户手动同步节拍或手动改歌词格式才能跑通。
- 单条失败导致整批中断或已生成文件损坏。
- 对现有网页版 app 的行为产生任何影响。

## 用户已定的决策

1. **终端向导**（方向键+空格多选），不做本地网页版。
2. **“主题”= app 里“一键随机”旁的主题列表**，即 `J.THEMES`（src/08b_omakase.js:45）：文字PV、动态文字、和风、恐怖、流行、抒情，外加“不指定主题”。选定主题后风格、配色、构图在主题方向内随机。
3. 歌词只支持**逐行时间戳**（LRC 的 `[mm:ss.xx]`，引擎 parseLyrics 直接认，毫秒精度没问题）。.trcx 以后再说。
4. 流程顺序：路径 → 配对识别报告 → 主题多选 → 比例 → 分辨率 → FPS → 摘要确认 → 开始。
5. **默认参数：720p / 30fps / 3:4**（用户指定；向导里仍可改选其他档位）。

## 评审核实记录

设计经独立实现者评审（[docs/BATCH_CLI_BUILDER_CHECK.md](BATCH_CLI_BUILDER_CHECK.md)），并在无头 Chrome 中**端到端实测跑通**：加载正式 index.html → 音频分析 → 主题随机 → plan → exportMP4，产出带 AAC 音轨的 720p MP4，零页面错误；同种子两次 plan 结构一致。实测参考耗时：约 3 分半的歌，720p/24 约 8 分钟、1080p/24 约 5 分钟、1080p/60 约 13 分钟每版本。评审发现的 4 个必须遵守的实现要点已并入下文管线（ensureFonts、audio 传 analyzeAudio 返回值、omakase 补丁合并、主题名中文映射）。

## 实现者可自定的细节（设计者的判断，已向用户声明过）

- **技术栈**：Python 3 + Playwright（注意：本机尚未安装，需 `pip install playwright && playwright install chromium`，约 100MB；评审时下载的 chromium headless shell 已留在本机缓存可直接用）+ questionary（交互）+ rich（进度）。入口 `python3 cli/jizura_batch.py`，依赖安装写进 README/注释。
- **配对规则**：同目录、同主文件名（不含扩展名）的音频+歌词为一对；音频扩展名认 mp3/m4a/wav/flac/ogg，歌词认 lrc/txt。同一主名有多个音频时按 mp3 > m4a > wav > flac > ogg 取一个（测试数据里出现过 mp3+wav 并存）。缺边的文件列入“未配对”提醒，不报错。默认只扫描一层目录（不递归）。
- **LRC 清洗**：网易云风格的 JSON 元数据行（以 `{` 开头、形如 `{"t":ms,"c":[...]}` 的作词/作曲行）会被引擎当歌词渲染，须过滤掉再喂给引擎。过滤在 CLI 侧做，不改原文件。文件按 utf-8-sig 读取（网易云导出常带 BOM）。
- **生成管线**（全部为现有引擎 API，页面加载仓库根目录的 index.html；评审已实测）：
  1. 起本地 HTTP 服务，同时服务仓库根（/）和输入文件夹（/input/）；
  2. 页面里 `fetch('/input/xx.mp3')` → `J.analyzeAudio(file)` 得节拍/时长。**`J.exportMP4` 的 audio 参数必须传这个返回值**（引擎读 `audio.buffer`，传 File 会静默产出无声视频）；
  3. `J.defaultProject()` + 歌词 + aspect/res/fps → `J.omakase(project, rnd, themeId)` 在主题内随机。**omakase 返回的是补丁，须 `Object.assign` 合并回 project**（同 12_ui.js 的做法）；rnd 用 `J.rng(种子)`（引擎自带播种 PRNG）；
  4. **导出前调 `J.ensureFonts(...)`**（网页版导出前必做；跳过则 Google Fonts 未加载、排版用回退字体，布局可能错）；
  5. `J.plan(project, audioInfo)` → `J.exportMP4({plan, project, audio, onProgress})` 得到 Blob，回传 Python 写盘。
- **主题名映射**：引擎里主题名是日文（`J.THEMES` 的 name 字段），CLI 自带 key→中文名映射（文字PV/动态文字/和风/恐怖/流行/抒情）。
- **输出**：输入文件夹**旁边（同级）**的 `output/` 目录——如输入 `/data/raw` 则输出 `/data/output`，不把产物混进原始数据目录。命名 `主文件名_主题中文名.mp4`；`output/jobs.json` 追加记录每条：时间、源文件、主题、种子、aspect/分辨率/fps、输出文件名、成败与错误信息。同名输出文件默认跳过，`--force` 重跑。**种子只记录，不做重放入口**（复现为结构级：纸纹理等帧内细节含未播种随机）。
- **失败处理**：单条失败记录后继续下一条；结束时汇总成功/失败清单。不做自动换种子重试。
- **浏览器与稳健性**：无头 Chromium（Playwright 默认）；需要网络加载 Google Fonts（离线时引擎自动回退本地字体，属可接受的降级）。长跑内存防护：每生成约 10 条 reload 一次页面。Ctrl-C 经 `signal`（AbortSignal）传入 exportMP4 干净中止。title/artist 从文件名拆（“歌手 - 歌名”，测试数据 lrc 内无 `[ti:]` 标签）。
- **依赖安装**：见技术栈条目；首次运行前需装好 Playwright 与 chromium。

## 约束

- 引擎、index.html、src/ 零改动；CLI 只是新目录 `cli/`。
- 串行生成；每条之间无需人工干预。
- 测试数据：`/Users/lixuan/Code_local/music_data/data/raw`（10 对平铺的 lrc+mp3，均含网易云 JSON 元数据行的清洗用例；song-0001/ 等子目录和 songs_index.json 属于用户另一套数据管线，v1 不解析、不递归进子目录）。

## 验收标准

1. 对测试文件夹全流程跑通：选 2 首歌 × 2 个主题，得到 4 个可播放的 MP4，时长与音频一致，歌词按 LRC 时间出现，节拍对齐，**音轨正常**（评审发现的“无声视频”坑的回归检查）。
2. jobs.json 里每条记录完整，种子可读。
3. 人为制造一条失败（如损坏的音频），整批不中断，最终汇总该条失败、其余成功。
4. 已存在的输出被跳过并有明确提示。
5. app 本身（index.html）无任何改动。
6. 默认参数不带修改直接回车走完向导时，得到 720p / 30fps / 3:4 的成片。
